## 2. 核心数据结构

### 2.1 会话重量 (deviceSessionWeights)

这是整个系统最核心的数据结构。它追踪每个设备托盘的实时重量变化。

```javascript
// 存储位置: mqtt-broker.js 全局 Map
// Key: 设备SN (如 "3000004157" 或 "device@586919357196537900@3000004157")
// Value: {
//   initialWeight: 985,    // 托盘初始重量(克) — 用户放盘时的重量
//   currentWeight: 785,    // 当前重量(克) — 实时更新
//   timestamp: 1786205331881
// }

// 取餐量 = initialWeight - currentWeight (即用户取走了多少克)
// 如果 currentWeight > initialWeight + 100g → 判定为"厨师放菜"，重置 initialWeight
```

**生命周期：**
- 首次收到设备重量上报时创建，TTL = 10分钟
- 每30秒检查一次，超过10分钟未更新的会话自动清除
- 取餐记录写入后会话不清除（保留供后续查询使用）

### 2.2 重量历史 (deviceWeightHistory)

用于跨上报周期的取餐判定，持久化到 SQLite。

```javascript
// Key: 设备SN
// Value: { weight: 985, timestamp: 1786205331881 }

// 用途：对比前后两次上报的重量差异
// diff = prevWeight - currentWeight
// diff > 50g  → 判定取餐
// diff < -50g → 判定厨师放菜(不记录)
// |diff| ≤ 50g → 忽略(正常波动)
```

### 2.3 设备重量缓存 (deviceWeightCache)

快速访问的临时缓存，供其他接口（如 VectorMaterial）读取。

```javascript
// Key: 设备SN / 客户端IP
// Value: { weight: 985, unit: 'g', timestamp: ..., source: 'mqtt' }
// TTL: 2分钟
```

### 2.4 菜品名智能解析 (resolveDishNameSmart)

设备上报时未必带完整的菜名，服务端通过多级兜底策略自动解析：

```
优先级:
  1. payload.menuName (设备直接传的)
  2. 设备SN → tray_display_devices.station_id → tray_stations.dish_name
  3. menuId 查 dish_nutrition / product_items / tray_stations
  4. device_dish_cache (历史缓存)
  5. dish_order_records (近2小时电子屏选菜)
  6. 兜底: "未知菜品"
```

## 3. MQTT 通道（推荐，低延迟）

### 3.1 设备 → 服务器：重量上报

```
Topic:   device-weight-info-report-v4.{merchantId}.{deviceSn}
         例如: device-weight-info-report-v4.586919357196537900.3000004157

QoS:     0

Payload:
{
  "ifTakeFoodState": false,     // true=强制取餐记录, false=普通重量变化
  "machineSn": "3000004157",    // 设备序列号
  "menuId": 8219,               // 菜品ID
  "menuName": "清汤米线",        // 菜品名称(可选)
  "menuWeigh": 985,             // ★ 当前托盘绝对重量(克)
  "menuPrice": 0,               // 单价(可选)
  "custId": 0,                  // 刷卡用户ID(可选)
  "merchantId": "586919357196537900"  // 租户ID(可选)
}
```

### 3.2 服务器处理流程（mqtt-broker.js）

收到 MQTT 重量消息后，服务端执行以下完整链路：

```
步骤1: 解析 payload
  ↓
步骤2: 更新设备在线状态
  updateDeviceStatus(sn, 'online')
  ↓
步骤3: 缓存重量（三级缓存）
  ├─ cacheDeviceWeight(sn, weight)       → deviceWeightCache (2min TTL)
  ├─ updateDeviceSessionWeight(sn, w)    → deviceSessionWeights (10min TTL)
  └─ deviceWeightHistory.set(sn, {w, ts}) → deviceWeightHistory + SQLite持久化
  ↓
步骤4: ★ 实时推送4个MQTT频道（见3.3节）
  ↓
步骤5: 智能解析菜名
  resolveDishNameSmart(dbQuery, { machineSn, menuId, menuName })
  ↓
步骤6: 取餐判定
  ├─ 有历史重量 ? 计算 diff = prevWeight - currentWeight
  │   ├─ diff > 50g   → 判定取餐，写入 tray_pickup_logs
  │   ├─ diff < -50g  → 判定厨师放菜，更新初始重量，不记录
  │   └─ |diff| ≤ 50g → 忽略波动
  ├─ ifTakeFoodState === true → 强制记录
  └─ menuWeigh 为负值(如-200) → 设备直接上报减少量，|menuWeigh|>50 则记录
```

#### 步骤6 详细：取餐记录的三个信号源

| 信号 | 来源 | 判定条件 |
|------|------|---------|
| `ifTakeFoodState=true` | payload 字段 | 设备明确告知"这是取餐" |
| `menuWeigh < -50` (负值) | payload 字段 | 设备直接上报变化量（如 -200g） |
| 历史对比 diff > 50g | 服务端自己算 | 当前重量比上次少了50g以上 |

**三个信号源 OR 关系，任意一个满足且 actualDrop > 50g 就生成记录。**

### 3.3 服务器 → 设备：实时推送（4个频道）

每次收到重量变化，服务端**同时往4个MQTT频道推送数据**，确保不同版本的设备固件都能收到更新：

```
═══════════════════════════════════════════════════════════════
频道1: device-update-menu-config-v4/{merchantId}/{deviceSn}
       用途: 完整营养+重量数据（最主要频道）
       格式:
       {
         "dishId": "8219",
         "dishName": "清汤米线",
         "targetWeight": 480,            // 日目标摄入量(克)
         "nutritionPer100g": {           // 每100g营养成分
           "calories": 124, "protein": 6.8, "fat": 5.2,
           "carbohydrate": 12.2, "dietaryFiber": 0, "calcium": 0
         },
         "initialWeight": 985,           // 托盘初始重量
         "currentWeight": 785,           // 当前重量
         "mealWeight": 200,              // ★ 取餐净重(克)
         "actualNutrition": {            // ★ 实际营养成分(已按取餐量换算)
           "calories": 248, "protein": 13.6, "fat": 10.4,
           "carbohydrate": 24.4, "dietaryFiber": 0, "calcium": 0
         }
       }
═══════════════════════════════════════════════════════════════
频道2: device-weight-control-v4/{merchantId}/{deviceSn}
       用途: 重量控制专用（轻量格式）
       格式:
       {
         "menuId": "8219",
         "menuName": "清汤米线",
         "initialWeight": 985,
         "currentWeight": 785,
         "mealWeight": 200,
         "actualNutrition": { ... },
         "timestamp": 1786205331881
       }
═══════════════════════════════════════════════════════════════
频道3: device-update-info-v4/{merchantId}/{deviceSn}
       用途: 信息更新通知（格式同频道1）
       格式: 同频道1
═══════════════════════════════════════════════════════════════
频道4: switch-device-menu-v4/{merchantId}/{deviceSn}
       用途: 切换菜品显示（含价格字段）
       格式:
       {
         "menuId": 8219,
         "dishesId": 8219,
         "menuName": "清汤米线",
         "productName": "清汤米线",
         "menuWeigh": 200,
         "weight": 200,
         "menuPrice": 0,
         "price": 0,
         "nutrition": { ... },
         "actualNutrition": { ... },
         "timestamp": 1786205331881
       }
═══════════════════════════════════════════════════════════════
```

### 3.4 其他 MQTT 频道

| 频道 | 方向 | 用途 |
|------|------|------|
| `time-calibration-v4` | 服务器→设备 | 时间校准，每20秒推送Unix毫秒时间戳 |
| `time-calibration` | 服务器→设备 | V1兼容版时间校准 |
| `device/{SN}/menu` | 服务器→设备 | 设备注册成功后推送完整菜品菜单(Retained消息) |

## 4. HTTP 通道（备用方案）

### 4.1 设备 → 服务器：重量上报

```
POST /api/weight/report
Content-Type: application/json

请求体:
{
  "sn": "3000004157",      // 设备序列号
  "key": "abc123",         // 设备密钥
  "weight": 985            // 当前托盘绝对重量(克)
}
```

**响应：**
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "current_weight": 985,       // 当前重量
    "net_weight": 985,           // 净重(当前-皮重)
    "log_created": true,         // ★ 是否生成了取餐记录
    "pickup_weight": 200         // 本次取餐量(克)
  }
}
```

**处理流程（routes-device.js）：**

```
步骤1: 验证 sn + key
  ↓
步骤2: 缓存重量
  ├─ cacheDeviceWeight(sn, weight) → deviceWeightCache
  └─ updateDeviceSessionWeight(sn, weight) → deviceSessionWeights
  ↓
步骤3: 查找关联的托盘站 (tray_stations)
  ├─ 有绑定 → 获取 lastWeight
  └─ 无绑定 → 自动创建默认托盘站
  ↓
步骤4: 取餐判定
  pw = lastWeight - weight
  如果 pw > 50g → 写入 tray_pickup_logs, log_created = true
  ↓
步骤5: 更新托盘站重量
  更新 tray_stations.hw_last_weight
  ↓
步骤6: 返回响应
```

> **注意：HTTP 上报不会触发 MQTT 4频道推送！**
> 如果设备用 HTTP 上报重量，它需要通过轮询 `get-main-device` 获取最新的营养数据。

## 5. 营养值计算公式

### 5.1 数据来源

营养计算需要两个数据源：

| 数据 | 来源 | 字段 |
|------|------|------|
| **每100g基准营养** | `dish_nutrition` 表 | `calories_per_100g`, `protein_per_100g`, `fat_per_100g`, `carbs_per_100g`, `dietary_fiber_per_100g` |
| **实际取餐重量** | 会话重量 | `mealWeight = initialWeight - currentWeight` |

> ⚠️ **列名对齐表**（dish_nutrition 数据库真实列名 vs 代码里用的字段名）：
> 
> | 数据库列名 | 代码读到的字段 | 说明 |
> |---|---|---|
> | `protein_per_100g` | `n.protein_per_100g` | 蛋白质 |
> | `fat_per_100g` | `n.fat_per_100g` | 脂肪 |
> | `carbs_per_100g` | `n.carbs_per_100g` | 碳水化合物 |
> | `dietary_fiber_per_100g` | `n.dietary_fiber_per_100g` | 膳食纤维 |
> | `calories_per_100g` | `n.calories_per_100g` | 热量 |
> | `target_weight` | `n.target_weight` | 目标重量 |
> | ❌ `calcium` | 不存在 | dish_nutrition 没有钙字段，前端默认 0 |
> 
> **新手常见坑：** 用 `SELECT protein, fat, calories FROM dish_nutrition` 会报错 `no such column: protein`。必须用完整列名 `protein_per_100g` 等。

### 5.2 计算公式

在 `routes-device.js` 的 `buildMainDeviceResponse()` 函数中：

```javascript
// factor = 实际取餐克重 / 100
const factor = mealWeight / 100;

// 实际营养 = 每100g基准 × factor
actualNutrition = {
  calories:      Math.round(calories_per_100g × factor × 10) / 10,
  protein:       Math.round(protein_per_100g  × factor × 10) / 10,
  fat:           Math.round(fat_per_100g      × factor × 10) / 10,
  carbohydrate:  Math.round(carbs_per_100g    × factor × 10) / 10,
  dietaryFiber:  Math.round(dietaryFiber_per_100g × factor × 10) / 10,
  calcium:       Math.round(calcium_per_100g  × factor × 10) / 10,
};
```

### 5.3 举例

```
菜品: 清汤米线
每100g营养: 热量124kcal, 蛋白质6.8g, 脂肪5.2g, 碳水12.2g
目标重量: 480g

场景: 用户取了200g

factor = 200 / 100 = 2.0

实际:
  热量 = 124 × 2.0 = 248.0 kcal
  蛋白质 = 6.8 × 2.0 = 13.6 g
  脂肪 = 5.2 × 2.0 = 10.4 g
  碳水 = 12.2 × 2.0 = 24.4 g
```

## 6. 设备 HTTP 轮询接口

### 6.1 get-main-device（核心查询接口）

设备通过此接口获取菜品信息 + 实时重量 + 实际营养。

```
GET /tengyun-api/api/v4/device/buffet/get-main-device
Headers:
  Machine-SN: 3000004157

可选参数:
  dishId=8219    指定菜品ID（不传则返回当前设备关联的首个菜品）
```

**响应（v2.0 新版扁平格式）：**
```json
{
  "code": 10000,
  "msg": "成功",
  "data": {
    "dishId": "8219",
    "dishName": "清汤米线",
    "targetWeight": 480,
    "nutritionPer100g": {
      "calories": 124, "protein": 6.8, "fat": 5.2,
      "carbohydrate": 12.2, "dietaryFiber": 0, "calcium": 0
    },
    "initialWeight": 985,
    "currentWeight": 785,
    "mealWeight": 200,
    "actualNutrition": {
      "calories": 248, "protein": 13.6, "fat": 10.4,
      "carbohydrate": 24.4, "dietaryFiber": 0, "calcium": 0
    }
  }
}
```

**数据来源链路：**
```
1. resolveDeviceSn(req) → 获取设备SN
2. 查询 tray_display_devices → 获取绑定模式
3. fetchTodayDishNutrition() → 从 dish_nutrition 查菜品+每100g营养
4. getDeviceSessionWeight(sn) → 从内存获取 initialWeight/currentWeight
5. 计算 mealWeight = initialWeight - currentWeight
6. 计算 actualNutrition = nutritionPer100g × (mealWeight/100)
```

### 6.2 bind-info-config/page（菜单列表）

```
GET /tengyun-api/api/v4/device/common/menu/bind-info-config/page
Headers:
  Machine-SN: 3000004157

Body:
{
  "content": {
    "applyDate": "2026-08-09",    // 查询日期
    "current": 1,
    "mealtimeType": 0,
    "size": 200
  }
}
```

**特点：** 此接口在返回菜单列表时，会**动态注入当前会话重量**。如果设备秤上正放着菜，会把对应菜品的 `weight` 替换为实际的 `mealWeight`。

### 6.3 接口速查

| 接口 | 方法 | 用途 | 营养数据 |
|------|------|------|----------|
| `/tengyun-api/api/v4/device/buffet/get-main-device` | GET | 单菜品详情+实时营养 | ✅ 含actualNutrition |
| `/tengyun-api/api/v4/device/common/menu/bind-info-config/page` | POST | 菜单列表+分餐段 | ✅ weight动态注入 |
| `/tengyun-api/api/v4/device/buffet/getsetting` | GET | 餐段+设备配置 | ❌ |
| `/api/weight/report` | POST | HTTP重量上报 | ❌ |
| `/tengyun-api/api/v4/device/common/base/exchange/key` | POST | 密钥交换 | ❌ |
| `/tengyun-api/api/v4/device/common/base/interval-config` | GET | 餐段时间配置 | ❌ |

## 7. 完整数据流时序图

```
时间轴 →

设备屏幕                     MQTT Broker                HTTP Server              服务端逻辑
   │                            │                          │                        │
   │ ① MQTT CONNECT            │                          │                        │
   │ ─────────────────────────→│                          │                        │
   │                            │                          │                        │
   │ ② PUB weight-info-report  │                          │                        │
   │ ─────────────────────────→│                          │                        │
   │                            │ ────────────────────────→│                        │
   │                            │                          │ ───→ 缓存重量          │
   │                            │                          │       缓存会话          │
   │                            │                          │       更新历史          │

   │   device-update-menu-     │                          │                        │

```

### 两种工作模式对比

| 特性 | MQTT模式 | HTTP轮询模式 |
|------|---------|-------------|
| 延迟 | 实时(<100ms) | 取决于轮询间隔(通常2-3秒) |
| 服务器推送 | ✅ 4频道主动推送 | ❌ 设备需主动轮询 |
| 网络开销 | 低(仅重量变化时推送) | 中(每次轮询完整HTTP请求) |
| 离线支持 | QoS 0, 断线后消息丢失 | N/A |
| 适用场景 | 推荐所有设备使用 | MQTT不可用时的备选 |

## 9. 常见问题排查

### Q1: 设备上报了重量，但屏幕没更新？

**MQTT 模式排查：**
1. 服务端日志搜索 `[MQTT Weight] ★ 推送实时重量` — 确认推送是否成功
2. 查看 `/api/mqtt/diagnose` 接口 — 确认4个频道都有消息
3. 确认 Topic 分隔符：服务器推送用 `/`，设备订阅用 `/`
4. 检查设备和服务端是否在同一局域网网段（`192.168.x.x`）

**HTTP 模式排查：**
1. 确认设备是否在轮询 `get-main-device`
2. 查看 `[BuffetExact]` 日志中的 `mealWeight` 值
3. 检查 `[SessionWeight]` 日志，确认会话重量已更新

### Q2: 营养数据始终为0？

1. 检查本地 SQLite `dish_nutrition` 表是否有当天的数据 (`menu_date` 字段)
2. 注意日期时区问题：北京时间 vs UTC 时间差8小时
3. 查看 `[fetchTodayDishNutrition]` 日志，确认是否命中数据
4. 兜底逻辑：`dish_nutrition` 无数据 → 回退到 `product_items`
5. ⚠️ **SQL 列名检查：** `dish_nutrition` 的营养列名为 `protein_per_100g` / `fat_per_100g` / `carbs_per_100g` 等，用 `SELECT protein` 会报 `no such column: protein`

### Q3: 取餐记录没有生成？

检查4个条件是否同时满足：
1. 有取餐信号(ifTakeFoodState / 负值变化量 / 历史对比减少)
2. 有历史重量可参考(hasPrevWeight = true)
3. 实际减少量 > 50g
4. 当前重量 < 上次重量

查看日志: `[MQTT Weight] ━━━ 取餐判断 ━━━`

### Q4: weight 值始终是 150 或 480？

```javascript
// product-data.js buildMealListFromProducts:
weight: Number(item.weight) || Number(item.target_weight) || 480.0

// 如果数据库里没有 target_weight 或 weight 字段，默认 480g
// 如果 buildRecipeDateListFromDishNutrition 中 dish_nutrition 也没有 target_weight，同样默认 480
```

### Q5: 局域网环境，日志里看到 "Supabase写入失败" 正常吗？

**完全正常。** 这是设计预期的行为：

```
[WARN][MQTT Weight] Supabase写入失败: TypeError: fetch failed
```

- 系统**优先写本地 SQLite**，取餐记录已成功写入本地数据库
- Supabase 云端同步是**可选的附加功能**，仅在能连外网时生效
- 局域网断开外网时，此警告不影响任何本地核心功能（重量采集、营养计算、MQTT推送、HTTP轮询全部正常）
- 设备屏幕的数据来自本地服务器，不经过 Supabase，所以完全不受影响

**一句话总结：看到这个警告可以忽略，所有本地功能正常工作。**

### Q6: 设备连不上 MQTT / HTTP？

1. 确认服务端已启动，日志中有 `MQTT Broker started on port 1883` 和 `HTTP Server listening on 8081`
2. 设备和服务端需要在同一局域网，互相能 ping 通
3. 检查防火墙是否拦截了 1883 / 8081 端口
4. MQTT 连接地址：`mqtt://{服务器局域网IP}:1883`
5. HTTP 接口地址：`http://{服务器局域网IP}:8081/...`

### Q7: 多个设备同时上报，数据会串吗？

**不会。** 每个设备通过 `deviceSn` 作为 key 隔离：
- `deviceSessionWeights` 按设备 SN 分别存储
- `deviceWeightCache` 按设备 SN 分别存储
- MQTT Topic 包含 `{merchantId}/{deviceSn}`，天然隔离
- SQLite 写入按 `sn` 字段区分
