## 联调前必读（5 分钟看完再动手）

### 网络拓扑

```
┌──────────────────────────┐
│  厂商 Android 设备        │
│  IP: 192.168.2.x         │
│  (自动获取/静态分配)       │
└────────┬─────────────────┘
         │ 局域网 Wi-Fi / 网线
         │
┌────────▼─────────────────┐
│  智慧餐盘本地服务器        │
│  IP: 192.168.2.xxx       │  ← 安装时确定，问现场管理员
│  HTTP: 8081              │
│  MQTT: 1883              │
└──────────────────────────┘
```

### 你的设备 SN 码

设备出厂时已烧录一个唯一 SN 码（如 `1000001751`），这是整个系统的**设备身份证**，所有接口都要用它。

**SN 码在你设备上通常长这样：**
- 型号标签上的序列号
- Android 系统设置 → 关于设备 → 序列号
- 固件代码里的 `Build.SERIAL` 或自定义字段

**确认方式：** 把 SN 码发给现场管理员，让他在后台「托盘管理 → 设备管理」里确认能查到这台设备。

### 第一步：测试网络连通性

```bash
# 在设备上 ping 服务器（或用 curl）
curl http://192.168.2.xxx:8081/api/ping
```

**收到这坨 JSON 就是通的：**
```json
{
  "code": 0,
  "msg": "pong",
  "data": {
    "clientIp": "192.168.2.101",
    "serverTime": "2026-07-27T08:30:00.000Z",
    "httpPort": 8081,
    "message": "如果你能看到这条JSON，说明网络是通的"
  }
}
```

如果 curl 不通，检查：
1. 设备和服务器连的是同一个路由器吗？
2. 服务器防火墙关了没？
3. IP 地址对不对？（问管理员）

## 完整联调流程（按这个顺序走，每一步都有验证方法）

```
步骤1: 设备注册       → 拿到 token + MQTT 地址
步骤2: 获取当前餐段     → 确认早/中/晚餐
步骤3: 获取菜品+营养    → 拿到菜名、营养成分、目标重量 ← 这是核心
步骤4: 上报重量        → MQTT 实时（推荐）或 HTTP 轮询
步骤5: 消费流水上报     → 取餐完成后上报记录
```

## 接口 1：设备注册

### 接口地址

```
POST http://{服务器IP}:8081/api/device/register
```

**也支持 GET（兼容不同设备 SDK），但推荐用 POST。**

### 请求方式

**方式 A：Header 传参（推荐）**

```
Headers:
  Machine-SN: 1000001751
  Machine-Key: abc123
```

**方式 B：Body 传参（Header 不可用时）**

```json
{
  "sn": "1000001751",
  "key": "abc123"
}
```

> SN = 设备序列号，Key = 设备密钥（出厂默认和 SN 相同，后台可修改）

### 响应（成功）

```json
{
  "code": 10000,
  "msg": "success",
  "data": {
    "token": "eyJkZXZpY2VfdG9rZW5fZXhhbXBsZV8xMjM0NTY3ODkwYWJjZGVm",
    "mqClientAddress": "mqtt://192.168.2.33:1883",
    "httpPort": 8081,
    "mqttPort": 1883,
    "tenantId": 1000000001,
    "deviceConfig": {
      "deviceUITemplate": "1",
      "ifBindplatebeforetakefood": "1",
      "weighAlarmModel": "1",
      "minimumsettlementweigh": "10",
      "stabledifference": "2",
      "alarmBelowHowGrams": "-1000",
      "maxWeightDish": "5000"
    }
  }
}
```

### 响应（设备不存在）

```json
{
  "code": 403,
  "msg": "验证失败",
  "data": null
}
```

→ 发 SN 码给管理员，让他在后台添加设备。

### 关键字段说明

| 字段 | 用在哪 | 说明 |
|------|--------|------|
| `token` | **所有后续接口的鉴权**，放 Header: `Authorization: Bearer {token}` | 有效期至设备断开 |
| `mqClientAddress` | **MQTT 连接地址**，直接 parse 出 host 和 port | 如 `mqtt://192.168.2.33:1883` |
| `minimumsettlementweigh` | 取餐最小结算重量（克） | 变化量小于此值不记录，防抖动 |
| `stabledifference` | 稳定差值（克） | 连续两次称重差值小于此值视为稳定 |
| `maxWeightDish` | 单盘最大重量（克） | 超过可能报警 |

### ⚠️ 常见坑

1. **code: 403 "验证失败"** → 设备还没在后台录入，找管理员加
2. **连接超时** → 防火墙、IP 不对、端口被改
3. **token 不要每次请求都重新注册**，注册一次缓存起来，只在 token 失效（接口返回 401）时重新注册

### 营养字段 → 屏幕映射（每 100g 含量）

| JSON 字段 | 单位 | 屏幕显示 |
|-----------|------|---------|
| `calories` | kcal | 热量 |
| `protein` | g | 蛋白质 |
| `fat` | g | 脂肪 |
| `carbohydrate` | g | 碳水 |
| `dietaryFiber` | g | 膳食纤维 |
| `calcium` | mg | 钙 |
| `weight` | g | **日目标摄入量**（如 480g） |

### 屏幕上的计算公式（在设备端本地算）

```
// 每次称重后实时计算
取餐量(克)    = 上次重量 - 当前托盘重量
目标进度(%)   = 取餐量 / dishes[0].weight × 100
剩余可拿(克)  = dishes[0].weight - 取餐量

蛋白质(克)    = 取餐量 / 100 × dishes[0].protein
碳水(克)      = 取餐量 / 100 × dishes[0].carbohydrate  
脂肪(克)      = 取餐量 / 100 × dishes[0].fat
膳食纤维(克)  = 取餐量 / 100 × dishes[0].dietaryFiber
钙(mg)        = 取餐量 / 100 × dishes[0].calcium
热量(kcal)    = 取餐量 / 100 × dishes[0].calories
```

### ⚠️ 常见坑

1. **dishes 数组为空** → 后台还没给这个设备绑定菜品，找管理员在「托盘管理」绑定
2. **weight 字段缺失或为 0** → 菜品没配置目标摄入量，默认可以设 480g
3. **多个菜品时 weight 怎么用** → 如果只显示一个目标进度条，`weight` 可以取所有菜品 weight 的总和，或只用第一个

## 接口 4：HTTP 重量上报（MQTT 不可用时的备选方案）

### 接口地址

```
POST http://{服务器IP}:8081/api/weight/report
```

### 请求

```json
{
  "sn": "1000001751",
  "key": "abc123",
  "weight": 456
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `sn` | string | 设备 SN 码 |
| `key` | string | 设备密钥 |
| `weight` | number | **当前托盘绝对重量（克）**，正整数 |

> ⚠️ weight 是**绝对重量**（托盘+食物的总重），不是变化量！

### 响应

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "current_weight": 456,
    "net_weight": 456,
    "log_created": true,
    "pickup_weight": 300
  }
}
```

- `log_created: true` → 服务器检测到取餐（当前重量比上次减少 > 50g），已自动记录
- `pickup_weight` → 本次取餐量（克），直接拿去更新屏幕上的「本次取餐」
- `log_created: false` → 没有发生取餐（重量变化 < 50g 或是增加），仅更新重量

### 轮询建议

设备每 2-3 秒上报一次当前重量，服务器自动判断是否取餐。

```
┌─ 定时器 (2-3s) ──────────────────────────────────────────────┐
│                                                               │
│  称重传感器 → 读当前重量 → POST /api/weight/report             │
│     ↓                                                         │
│  解析响应 → log_created == true ? 更新「本次取餐」: 啥也不做  │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

## MQTT 方案（推荐，低延迟）

> 如果设备端 MQTT 不好集成，可以先用 HTTP 轮询方案（接口4），功能完全一样。

### MQTT 连接参数

从接口 1（设备注册）响应中拿到 `mqClientAddress`，解析出 host 和 port：

```kotlin
// Android 示例
val mqttUrl = "mqtt://192.168.2.33:1883"
val host = mqttUrl.substringAfter("mqtt://").substringBefore(":")  // "192.168.2.33"
val port = mqttUrl.substringAfterLast(":").toInt()                  // 1883
```

| 连接参数 | 值 | 说明 |
|----------|-----|------|
| ClientID | 设备 SN 码 | 如 `1000001751` |
| Username | 设备 SN 码 | 同上 |
| Password | 设备密钥（hw_key） | 默认和 SN 相同 |
| Protocol | MQTT 3.1.1 | |
| Keep Alive | 60 秒 | |

### MQTT 发布 Topic：重量上报

```
Topic: device-weight-info-report-v4.1000000001.{设备SN}

例如: device-weight-info-report-v4.1000000001.1000001751
```

> 固定 merchantId = `1000000001`

**Payload A — 实时重量变化（每 1-2 秒发一次）：**

```json
{
  "ifTakeFoodState": false,
  "machineSn": "1000001751",
  "menuId": 100001,
  "menuName": "红烧肉",
  "menuWeigh": 985,
  "custId": 0
}
```

> `menuWeigh` = **当前托盘绝对重量**（克），正数。
>
> `ifTakeFoodState: false` = 这只是重量变化，不是取餐确认。

**Payload B — 确认取餐完成（用户端走/超时后发一次）：**

```json
{
  "ifTakeFoodState": true,
  "machineSn": "1000001751",
  "menuId": 100001,
  "menuName": "红烧肉",
  "menuWeigh": 785,
  "custId": 10001
}
```

> `ifTakeFoodState: true` → 强制触发取餐记录。`custId` 可选，刷卡时传。

### 服务器取餐自动识别逻辑

你不需要在设备端计算取餐量，服务器自动做：

1. 收到重量 985g → 记录为「首次重量」，不生成取餐记录
2. 收到重量 785g ↓ → 差值 200g > 50g → 自动记录取餐 200g
3. 收到重量 1000g ↑ → 这是增加（厨师放菜），不生成取餐记录
4. `ifTakeFoodState: true` → 无论差值多少，强制记录

### MQTT 订阅 Topic：接收菜品菜单

```
Topic: device/{SN}/menu

例如: device/1000001751/menu
```

设备注册成功后，服务器会自动向这个 Topic 推送**保留消息**（retained），MQTT 连接后立刻收到。Payload 内容和接口 3 一样：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "dishes": [ "... 和接口3的dishes数组一样 ..." ],
    "deviceConfig": { "...": "..." }
  }
}
```

### MQTT 时间校准

```
Topic: time-calibration-v4
```

服务器每 20 秒推送一次 Unix 时间戳（毫秒），设备可用于对时：

```
Payload: "1722041400000"  ← 纯字符串，直接 parseInt 得到毫秒时间戳
```

```
Topic: time-calibration   ← 兼容旧版 V1 设备
```

## 接口 5：取餐消费流水上报

### 接口地址

```
POST http://{服务器IP}:8081/api/v4/device/buffet/upweightmenu
```

### 什么情况下调这个接口

- 用户刷卡取餐，需要记录 `custId`（人员信息）
- MQTT 不可用，用 HTTP 上报消费记录
- 设备端自己判断取餐完成后主动上报

### 请求

```json
{
  "content": {
    "deviceSn": "1000001751",
    "menuId": 100001,
    "menuName": "红烧肉",
    "weight": 785,
    "menuWeigh": 200,
    "quantity": 1,
    "custId": 0,
    "macNo": "1000001751",
    "macSerial": "SN001",
    "macTime": "2026-07-27 12:30:00"
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `deviceSn` | string | ✅ | 设备 SN 码 |
| `menuId` | number | ✅ | 菜品 ID（来自接口3的 `dishesId`） |
| `menuName` | string | ✅ | 菜品名称（来自接口3的 `productName`） |
| `menuWeigh` | number | ✅ | **本次取餐重量（克）**，不是绝对重量！ |
| `weight` | number | 选填 | 取餐后托盘绝对重量 |
| `custId` | number | 选填 | 刷卡用户 ID，无刷卡传 0 |
| `quantity` | number | 选填 | 份数，默认 1 |
| `macTime` | string | 选填 | 设备本地时间 |

> ⚠️ 注意区分：
> - `menuWeigh` = 本次取走了多少克（如 200g）
> - `weight` = 取完后托盘还剩多少克（如 785g）

### 响应

```json
{
  "code": 0,
  "msg": "",
  "data": null
}
```

## 开发阶段快速验证脚本

把下面 curl 命令里的 IP 换成实际服务器 IP，一条条跑：

```bash
# 设置变量
SERVER="192.168.2.33:8081"
SN="1000001751"
KEY="abc123"

# 1. 连通性
curl -s http://$SERVER/api/ping | python3 -m json.tool

# 2. 设备注册
curl -s -X POST http://$SERVER/api/device/register \
  -H "Machine-SN: $SN" \
  -H "Machine-Key: $KEY" | python3 -m json.tool

# 3. 获取餐段
curl -s http://$SERVER/tengyun-api/api/v4/device/buffet/getsetting \
  -H "Machine-SN: $SN" | python3 -m json.tool

# 4. 获取菜品 (把 TOKEN 换成上一步拿到的)
TOKEN="eyJkZXZpY2VfdG9rZW5f..."
curl -s http://$SERVER/tengyun-api/api/v4/device/buffet/get-main-device \
  -H "Machine-SN: $SN" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

# 5. 上报重量 (模拟托盘 985g)
curl -s -X POST http://$SERVER/api/weight/report \
  -H "Content-Type: application/json" \
  -d "{\"sn\":\"$SN\",\"key\":\"$KEY\",\"weight\":985}" | python3 -m json.tool

# 6. 再上报 (模拟取餐后 785g，差值 200g > 50g 会自动记录)
curl -s -X POST http://$SERVER/api/weight/report \
  -H "Content-Type: application/json" \
  -d "{\"sn\":\"$SN\",\"key\":\"$KEY\",\"weight\":785}" | python3 -m json.tool
```

## 完整数据流总结

```
                 ┌──────────────────────────┐
                 │     厂商 Android 设备      │
                 └──────────┬───────────────┘
                            │
       ① POST /api/device/register (SN + Key)
          ← token, mqttAddress
                            │
       ② GET /tengyun-api/.../get-main-device (SN + token)
          ← dishes[{ name, calories, protein, fat, carbs,
                     fiber, calcium, weight:480 }]
                            │
       ③ 称重传感器读数 (每 2s)
          │
          ├─ MQTT: device-weight-info-report-v4.1000000001.{SN}
          │    { menuWeigh: 985, ifTakeFoodState: false }
          │
          └─ HTTP: POST /api/weight/report
               { sn, key, weight: 985 }
                            │
                            ▼
       ④ 设备端本地计算 (每次重量更新)：
          取餐量 = 上次重量 - 当前重量
          目标%  = 取餐量 / 480 × 100
          蛋白质 = 取餐量 / 100 × 13.5
          ...
                            │
                            ▼
       ⑤ 屏幕实时更新显示：
          ┌──────────────┐
```

## 常见问题速查

| 现象 | 原因 | 解决 |
|------|------|------|
| `/api/ping` 不通 | 网络不通 | 检查 IP、防火墙、同一个路由器 |
| 注册返回 403 | 设备没录入 | 发 SN 码给管理员 |
| dishes 为空 | 没绑定菜品 | 管理员在「托盘管理」绑定 |
| 重量上报返回 404 | station 不存在 | 首次上报时服务器会自动创建 |
| `pickup_weight` 始终为 0 | 重量变化 < 50g | 先用大差值测（从 2000 降到 500） |
| 取餐记录没显示 | 餐段时间外 | 确认当前时间在餐段内（午餐 10:30-13:30） |
| token 失效 401 | 设备重连了 | 重新调接口1拿新 token |
